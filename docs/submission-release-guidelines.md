# 제출용 Release 작업 가이드라인

기준일: 2026-11-04 (한국 시간) / 상태: 빌드 변형·공유 소스셋 분리 및 컴파일 검증 완료. 실제 정차 판별 연결·Debug 전환 시험 완료. 서명·제출 APK 및 Release 런타임 검증 전.

이 문서는 동행길의 제출용 APK와 시연 범위를 판단하는 공통 기준이다. 기능·빌드·권한·시연 관련 작업 전에 읽고, 변경한 범위와 검증 결과는 `docs/work-log.md`에 남긴다. 현재 코드가 이 문서의 모든 기준을 이미 충족하는 것은 아니다.

## 1. 공식 제출 조건과 프로젝트 결정의 구분

공식 제출 안내에서 확인한 조건:

- 접수양식(기획서)은 필수이며 개발 산출물은 선택 제출이다. 1차 시연에는 목업·프로토타입·화면 녹화도 인정된다.
- GitHub 제출 시 소스와 실행 가능한 Release APK를 포함한다. APK 위치는 `apk/`, 파일명은 `팀명_앱이름_release.apk`다.
- README에 앱 소개, 실행 방법, 테스트 환경·필요 설정, APK 위치 또는 Release 링크를 적는다.
- 2차 PT 대상 팀은 PT 전 실제 동작 가능한 앱을 완료해야 한다. 1차 산출물은 PT 전까지 보완할 수 있다.

출처 (2026-11-04 확인):
- [지원·제출 방법](https://appdevchallenge.auto-hmg.io/guide/submission)
- [심사·시상](https://appdevchallenge.auto-hmg.io/guide/judging-awards)

이후의 시연 모드 구성·서명 관리·검증 항목은 프로젝트가 정한 품질 기준이다. 심사 통과나 가산점 획득을 보장하지 않는다. 제출 직전 공식 공고를 재확인한다. 실차 시연이 필수라고 가정하지 않고 운영 측의 별도 지침을 따른다.

## 2. 이번 제출 범위 결정

1차 제출용 APK에는 **실제 내 차량 정보와 명확히 구분된 모의 동행 시연**을 함께 제공한다. 초기 실행은 실제 정보 모드이고, 정차가 확인된 상태에서만 사용자가 모의 시연에 진입한다. 미완성 통신 때문에 앱 전체가 실행되지 않도록 구성하지 않는다.

모의 기능을 포함한 1차 프로토타입과 실제 통신 구현 완료를 구분한다. 두 에뮬레이터 사이 실제 송수신은 로컬 중계로 검증하며, 공식 앱 연동 지원 확인이 되지 않았다는 이유만으로 다른 지원 가능한 통신 방식의 검증을 막지 않는다. SharingTransport 교체 구조는 유지한다.

## 3. 실제 정보와 모의 시연 표시 원칙

- 실행 첫 화면은 실제 Pleos 정보다. SDK 연결·권한·목적지가 없으면 해당 상태를 안내하고, 가상 값으로 자동 대체하지 않는다.
- 모의 화면에 진입 전 ‘실제 차량 정보가 아닌 가상 시연이며 외부로 전송하지 않음’을 안내한다. 화면 전체에 지속적인 모의 표시를 둔다.
- 모의 차량명·주소·메시지·전달·확인은 모두 가상임을 명시한다. 가상의 상대 확인을 실제 수신 증거로 표시하지 않는다.
- 공식 앱 로고·가짜 로그인·가짜 연결 완료 화면을 만들지 않는다.
- 모의 모드에는 실제 GPS·내비 목적지 데이터를 주입하거나 저장·외부 전송하지 않는다.
- 같은 목적지의 차량끼리만 ETA 비교를 표시하고, 오래된 상태·연결 끊김에서는 확정 ETA를 숨긴다.
- 모의 종료·화면 이탈·프로세스 재시작 시 모의 그룹과 메시지를 지운다. 실제 정보 화면은 SDK에서 새로 조회한다.
- 영상·기획서·README도 실제 SDK 연동, 모의 공유, 미구현 목표를 구분한다.

## 4. 빌드 구성 기준과 적용 상태

standard/submission flavor와 debug/release build type을 적용했다. `src/demo`에는 모의 UI·엔진·비공개 Activity 선언만 두고, Debug와 submissionRelease에서만 공유한다. 네 변형의 컴파일·매니페스트와 104개 구성 검사를 통과했다. **실제 그룹 설정의 속도·기어·UX 상태 게이트는 모든 변형에 적용한다. 모의 시연 게이트는 모의 기능이 있는 Debug와 submissionRelease에 공통 적용했다. 서명된 APK나 Release 런타임 시험은 아직 없다.**

- 제출 변형은 `submissionRelease`로 구성한다. Release build type을 사용하고 debuggable=false로 설정한다.
- 일반 실행용 `standardRelease`는 모의 시연 진입점·모의 구현을 포함하지 않는다. 제출용과 일반용 차이는 빌드 시 결정한다.
- 제출용에서 재사용할 모의 엔진·시연 UI는 전용 demo 소스셋 등으로 분리해 Debug와 submission에서만 포함한다. `src/debug` 전체를 Release에 끌어오지 않는다.
- 시연 포함 여부는 BuildConfig.DEBUG와 별도인 명시적 빌드 설정으로 관리한다. Release의 DEBUG 값을 켜서 우회하지 않는다.
- SDK 진단·알림 시험은 계속 Debug 전용이다. 제출 시연 Activity는 앱 내부에서만 열고 exported=false로 한다. DUMP 권한을 요구하는 셸 테스트 진입점에 의존하지 않는다.
- 같은 앱을 업데이트하는 submissionRelease의 applicationId는 현재 `io.demo.companion`을 유지한다. 별도 테스트 패키지가 필요하면 그 목적과 설치 방법을 먼저 정한다.
- flavor 적용 시 기존 assembleDebug/assembleRelease가 여러 변형을 만들 수 있으므로 빌드 스크립트 호출·README·APK 선택 검증을 함께 갱신한다. 현재 사용 가능한 명령과 아직 없는 assembleSubmissionRelease를 혼동하지 않는다.
- 두 변형을 동시에 설치하는 시연은 이번 기본 구성에 포함하지 않는다. Debug와 Release 서명이 달라 기존 앱 위에 설치가 실패하면 전용 깨끗한 테스트 에뮬레이터에서 검증한다. 사용자 앱을 임의로 삭제하지 않는다.

## 5. 주행 안전 기준

다음은 적용·검증할 프로젝트 기준이다. 모의 시연의 실제 AAOS 게이트 구현과 Debug 검증은 [정차 안전 문서](parking-safety.md)에 기록했다. 화면 제목에 ‘정차 중’이라고 적거나 distractionOptimized를 선언한 것만으로 완료 처리하지 않는다.

- 지원되는 차량 상태 SDK로 정차 여부를 판별한다. 모의 시연은 속도 정확히 0m/s·기어 P·UX 제한 없음, 1초 유지·3초 이내 신선도 조건을 사용한다.
- 상태 미수신·오래됨·연결 실패는 정차로 간주하지 않는다. 모의 진입과 그룹 코드 입력 등 주의가 필요한 조작을 제한한다.
- 주행이 감지되면 모의 시연을 종료하거나 잠그고 안전한 화면으로 이동한다. 개발용 가상 차량 값으로 이 제한을 해제하지 않는다.
- 주행 중 실제 정보 화면은 읽기 중심으로 제한하고 과도한 스크롤·입력·알림을 줄인다. 메시지 조작 범위는 안전 검증 후 결정한다.
- Virtual Console에서 정차→주행, 주행→정차, 상태 갱신 중단을 시험한다. 에뮬레이터 결과를 실차 안전성 승인으로 설명하지 않는다.

## 6. Release 서명 기준

- 제출 전용으로 관리하는 Release 키를 사용한다. Debug 키로 서명하거나 Debug APK의 이름만 바꿔 제출하지 않는다.
- 동일 앱의 후속 제출·업데이트는 같은 Release 키를 유지하고 versionCode를 올린다. versionName은 실제 제출 단계와 구현 범위를 표현한다.
- 키는 저장소 밖의 사용자 관리 경로에 두고 별도 백업한다. 실제 키 위치·alias·비밀번호는 생성 시 정한다. 이번 문서 작성에서는 키를 생성하지 않는다.
- Gradle은 사용자 환경변수 또는 Git 제외된 로컬 서명 설정에서 값을 읽는다. 비밀번호를 build.gradle·README·로그·명령행 인자에 직접 넣지 않는다.
- 필요한 서명 값이 없으면 해당 Release 빌드를 명확히 실패시킨다. unsigned APK나 Debug 서명으로 조용히 대체하지 않는다.
- keystore, 비밀번호 파일, 서비스 계정 키는 Git·APK·공유 문서에 포함하지 않는다. 공개 가능한 인증서 지문과 APK SHA-256만 검증 기록에 남긴다.
- 현재는 `verifyReleaseDistributionConfigured`가 모든 Release APK/AAB 패키징을 실패시킨다. 컴파일·매니페스트 검증은 가능하며, 후속 서명 작업에서 이 차단을 실제 서명·준비 상태 검증으로 교체한다. 임의 우회 옵션이나 Debug 서명 fallback은 제공하지 않는다.
- 서명 검증과 실제 설치·실행 검증은 별도다. 도구의 서명 검사 성공만으로 제출 준비 완료라고 하지 않는다.

## 7. 산출물과 완료 조건

실제 팀명은 아직 정하지 않았다. 현재 저장소의 `artifacts/donghaeng-gil-demo-debug.apk`는 개발용이며 제출용으로 취급하지 않는다. 최종 제출 경로는 `apk/<확정팀명>_동행길_release.apk`로 정한다. `.gitignore`의 apk 폴더 예외와 README를 실제 산출물 생성 시 함께 수정한다. placeholder 이름의 APK를 제출하지 않는다.

제출용 APK 생성 작업의 완료 조건:

- [ ] 포함 범위와 현재 구현 차이를 해소하고 submissionRelease가 debuggable=false인지 검사
- [ ] 실제 정보 초기 실행과 명시적 모의 진입·종료 확인
- [ ] 주행·정차·상태 미확인 시 조작 제한 검증
- [ ] SDK 진단·강제 경로 시험·알림 시험 Activity가 제출 APK에서 제외됨을 manifest·dex로 확인
- [ ] 모의 화면은 비공개 진입점이며 공식 앱 연동을 완료한 것처럼 표시하지 않음
- [ ] 모든 기존·추가 검사 및 해당 Release 빌드 통과
- [ ] Release 키로 서명하고 인증서·APK SHA-256 및 서명 검사 결과 기록
- [ ] 최종 서명 APK를 새 테스트 환경에 설치해 실제 화면·모의 시연·실패 상태를 확인
- [ ] APK 파일명·경로·versionCode·versionName·소스 커밋을 기록하고 README 실행 방법 갱신
- [ ] 영상과 기획서에 실제/모의/향후 기능을 일관되게 설명
- [ ] Git에 키·로컬 설정·개인정보가 없는지 확인

사용자의 실제 중계 구현 요청에 따라 INTERNET 권한과 별도 실제 공유 화면을 추가했다. 명시적 동의 후 좌표·주소·목적지·ETA를 location Foreground Service로 전송하며 다른 앱에서도 유지한다. 지속 알림의 중지, 탈퇴·권한/설정 해제·작업 종료 시 중지하며 자동 재시작하지 않는다. [백그라운드 공유 기준](background-sharing.md)을 따른다. Debug는 지정된 로컬 호스트 HTTP만, Release는 HTTPS만 허용한다. 실제 그룹 화면의 정차 설정·메시지 조작 게이트를 위해 CAR_SPEED/CAR_POWERTRAIN을 모든 변형에서 사용한다. 임시 인증·그룹 격리·보관 제한과 온라인 이전 한계는 [실제 중계 문서](local-relay.md)를 따른다.

## 8. 적용 순서와 변경 관리

1. 제출 변형과 모의 소스셋 구조 구성 완료. `scripts/verify-build-variants.ps1`로 컴파일·구성을 재검증할 수 있다.
2. 모의 시연의 실제 주행·정차 게이트 및 Debug 전환 검증 완료. 이후 최종 Release에서도 동일한 제한을 설치·실행 검증한다.
3. 팀명·서명 키 보관 방법을 확정하고 서명 설정을 연결한다.
4. 제출 APK를 생성·검증하고 영상·기획서 작성에 사용한다.
5. 실제 통신은 별도 작업으로 진행하고, 검증된 경우에만 이 범위와 설명을 갱신한다.

새 기능을 요청받으면 포함/별도 작업/제외 중 어디에 속하는지 검토한다. 범위를 바꾸는 경우 이 문서와 작업 기록을 함께 갱신하고 근거를 남긴다. 사용자의 최신 지시와 상위 작업 규칙이 우선한다. 문서만 수정한 작업에는 불필요한 빌드·키 생성·커밋·푸시를 수행하지 않는다.

## 9. 개발 중 검증과 최종 제출 파일 생성

개발 중에는 Debug로 기능을 확인하고, 기능·권한·소스셋·빌드 설정 변경 시 submissionRelease의 컴파일·구성 검사도 유지한다. 공통 소스의 변경은 제출 변형에도 자동 반영되므로 완성 시 별도 앱 복사본으로 코드를 이식하지 않는다.

기능 범위를 확정한 뒤 Release 서명 설정, versionCode/versionName, APK 생성·최종 설치·시연 검증, 파일명·README·영상 정리를 한 차례 제출 마무리 작업으로 묶을 수 있다. 다만 서명 인증서 차이, Release 전용 동작, 필요한 외부 서비스의 패키지·인증서 등록, 최종 시연 재현성은 컴파일만으로 확인되지 않으므로 제출 직전까지 검증을 미루지 않는다. 최종 생성·설치 검증 뒤 코드를 바꾸면 해당 APK와 검증 기록도 다시 맞춘다.

## 2026-11-06 그룹 접근 통제

실제 HTTP 공유의 그룹장 역할·초대 코드 재발급/폐기·참여 승인/거절·강제 퇴장을 구현했다. [그룹 접근 기준](group-access-control.md)을 공통 기준으로 사용한다. 승인 전에는 그룹 정보가 제공되지 않으며 승인 후에도 각 차량의 명시적 위치 공유 동의가 필요하다. 실제 공유의 관리 조작은 정차·연결·역할 확인을 적용하고 주행 중 관리 목록을 숨긴다. 모의 엔진에는 이 서버 접근 제어를 적용한 것처럼 설명하지 않는다.

계정/차량 소유 인증, 온라인 HTTPS 배포, 그룹장 양도, 실차·서명된 Release 실행은 여전히 후속 범위다. API accessVersion 2를 지원하는 앱/서버를 함께 사용한다. Release 키·제출 APK 차단은 유지한다.
